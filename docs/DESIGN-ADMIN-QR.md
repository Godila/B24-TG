# DESIGN-ADMIN-QR — QR-онбординг менеджера (спайк, план 010)

Дата: 2026-08-14. Статус: спайк завершён (код + мок-тесты); живой эксперимент
со сканом реального QR — **не проводился** (шаг оператора, см. ниже).

Зачем: сегодня онбординг менеджера = SSH → SQL → интерактивный CLI (SMS-код/2FA)
→ рестарт bridge. Telethon умеет `qr_login()`: менеджер сканирует QR своим
TG-приложением — без SMS-кода. Спайк проверяет, вписывается ли этот флоу в
нашу архитектуру (web стартует логин, bridge потом регистрирует сессию).

Прототип: `src/app/web/routes/admin_qr.py` + `src/app/static/qr.html`
(vendored `static/vendor/qrcode.min.js`). Маршруты — только при
`DEV_MODE=true`, иначе 404.

---

## 1. Факты Telethon (по установленному исходнику `.venv/Lib/site-packages/telethon`)

1. **Сигнатура**: `async def qr_login(self, ignored_ids: List[int] = None) -> QRLogin`
   — `client/auth.py:491`. Клиент обязан быть **подключен** до вызова
   (`await client.connect()`; докстринг `client/auth.py:495-496`: «you must be
   connected before invoking this»).
2. **Первый запрос**: `qr_login()` сразу вызывает `await qr_login.recreate()`
   (`client/auth.py:527-528`), который отправляет `auth.ExportLoginTokenRequest`
   (`tl/custom/qrlogin.py:22-27`; сам запрос собирается в `__init__`,
   `qrlogin.py:16-19`). То есть «старт QR» = один RPC; отдельного рукопожатия нет.
3. **URL для QR-картинки**: `QRLogin.url` — строка вида
   `tg://login?token=<base64url(token)>` (`qrlogin.py:41-57`). Именно её нужно
   кодировать в QR (сервер не рендерит картинку). Токен также доступен как bytes
   (`QRLogin.token`, `qrlogin.py:30-38`).
4. **Время жизни токена**: `QRLogin.expires` — серверный datetime истечения
   (`qrlogin.py:59-66`). На практике ~2-3 мин на итерацию. После истечения —
   `recreate()` (новый токен и новый url — фронт обязан перерисовать QR).
5. **wait() обязан исполняться во время скана**: докстринг `qrlogin.py:74-77`:
   «must be executing while the QR code is being scanned. Otherwise, the login
   will not complete». Реализация: `wait()` вешает raw-обработчик на
   `UpdateLoginToken` и ждёт `asyncio.Event` через `wait_for`
   (`qrlogin.py:93-103`); дефолтный таймаут = время до `expires`
   (`qrlogin.py:90-91`); по таймауту — `asyncio.TimeoutError` (`qrlogin.py:78-79`).
6. **Успех — без кода подтверждения**: после скана `wait()` повторно отправляет
   `ExportLoginTokenRequest`; если токен импортирован — обрабатывает
   `LoginTokenMigrateTo` (переезд на другой DC: `_switch_dc` + повторный
   `ImportLoginTokenRequest`, `qrlogin.py:108-111`) и на `LoginTokenSuccess`
   вызывает `_on_login(user)` — **сессия авторизована сразу**, возвращён User
   (`qrlogin.py:114-117`). SMS-код не запрашивается вовсе.
7. **2FA cloud-пароль НЕ обходится** (проверено по исходнику, ответ на вопрос
   из плана): докстринг `client/auth.py:524-525` — «If you have 2FA enabled,
   `wait` will raise `telethon.errors.SessionPasswordNeededError`. You should
   except that error and call `sign_in` with the password». Ошибка вылетает из
   повторного `ExportLoginTokenRequest` (`qrlogin.py:108`): сервер требует SRP-
   пароль. Завершение: `await client.sign_in(password=...)` (`client/auth.py:270-275`,
   SRP через `password_mod.compute_check`, `client/auth.py:342-345`).
   Вывод: QR работает и с 2FA, но нужен ДОПОЛНИТЕЛЬНЫЙ шаг — поле ввода пароля
   после скана. В прототипе это статус `error` с подсказкой идти в CLI.
8. (Справочно) `log_out()` удаляет .session-файл (`client/auth.py:531-557`,
   удаление на `:555`) — пригодится для «отвязки аккаунта» (вне scope спайка).

## 2. Что сделано в спайке

- `GET /dev/qr` — страница (`static/qr.html`): форма (b24_user_id, phone) →
  `/start` → QR рисуется на клиенте (vendored `qrcode.min.js`, qrcodejs 1.0.0
  с cdnjs, 19.9 KB — jsdelivr/unpkg из этой сети недоступны) → опрос `/status`
  каждые 2 с → при `recreate()` QR перерисовывается по новому `qr_url`.
- `GET /dev/qr/start?b24_user_id&phone` — find-or-create Manager+TgAccount
  (по образцу `scripts/seed_manager.py`; заглушечный phone обновляется, чужой
  phone → 409), `.session` создаётся по path-контракту
  `<tg_sessions_dir>/account_<id>/session`, затем `client.qr_login()`;
  логин-корутина (`wait()` → таймаут → `recreate()`, до 3 итераций) живёт в
  фоне (`asyncio.create_task`); на успех — `TgAccount.status=active` в БД.
- `GET /dev/qr/status?account_id` → `waiting|authorized|expired|error` (+текущий
  `qr_url`, +`error`). Состояние — in-memory dict (теряется при рестарте web).
- `docker-compose.yml`: volume `tg_sessions` дополнительно смонтирован в `web`
  (эксперимент, следствия — ниже).
- Всё гейтится `settings.dev_mode` → 404 (паттерн dev-GET из `placement.py`).
- Тесты: `tests/unit/test_admin_qr.py` — 12 мок-тестов (TelegramClient заменён
  моком), включая 2FA/timeout/recreate/409/повторный старт.

## 3. Архитектура: где должен жить QR-логин — web vs bridge

Ключевой факт: web и bridge — разные контейнеры; volume `tg_sessions` был
смонтирован только в bridge. QR-логин из web пишет .session в FS web — bridge
его не увидит. Варианты:

### Вариант A — монтировать tg_sessions в web (сделано в спайке)

web сам запускает `qr_login()` и пишет .session в общий volume.

- Плюсы: минимум движущихся частей; Telethon уже в том же образе (один
  Dockerfile); мост между «браузером» и «TG-клиентом» прямой.
- Минусы/риски:
  - **Безопасность**: web — процесс, доступный из интернета через nginx; теперь
    он имеет RW-доступ ко ВСЕМ сессионным файлам (взлом web = кража всех
    сессий). В dev — приемлемо, в prod — расширение blast radius.
  - **Блокировка .session**: если аккаунт уже зарегистрирован в bridge, два
    процесса откроют один SQLite-файл. Telethon/SQLite переживёт кратковременный
    доступ (файловые локи), но это нарушение инварианта «один файл — один
    владелец». В спайке смягчено тем, что QR-онбординг нужен для НОВЫХ
    аккаунтов, которых bridge ещё не трогает.
  - Рестарт web посреди логина — см. «Открытые вопросы» №5.

### Вариант B — команда bridge через таблицу в БД (рекомендуется для prod)

web пишет строку в таблицу-очередь (`login_commands`: account_id, phone,
status=pending), bridge своим поллером (паттерн outbox/crm_sync уже есть)
подхватывает, сам делает `qr_login()`, кладёт `qr_url` и статус обратно в БД;
web только читает строку и отдаёт браузеру.

- Плюсы: единственный писатель .session — bridge (инвариант сохранён); web не
  получает доступ к session volume вообще (откат изменения docker-compose);
  переиспользуется проверенный паттерн поллера; 2FA-пароль можно принимать
  тем же каналом (команда `submit_password`).
- Минусы: больше кода (таблица + статусная машина + поллер); задержка
  появления QR = интервал полла (секунды — неощутимо).

### Вариант C — отдельный login-контейнер

One-shot джоба с монтированным volume: пишет сессию, обновляет БД, умирает.

- Плюсы: изоляция web и bridge.
- Минусы: чтобы web запускал контейнеры, нужен docker socket внутри web —
  дыра хуже варианта A; либо внешний оркестратор — лишняя сущность для
  одного онбординга в неделю. Отвергнут.

| Критерий | A (volume в web) | B (команда в БД) | C (login-контейнер) |
|---|---|---|---|
| Код | минимум | средне | много |
| Доступ web к сессиям | да (риск) | нет | нет |
| Один писатель .session | нет (нарушен) | да | почти (по расписанию) |
| 2FA-пароль | через web | через web→БД→bridge | отдельно |
| Оркестрация | нет | нет | docker socket/внешняя |

**Решение**: спайк/локально — A (оставляем как есть); продакшен — B.

## 4. Supervisor-гейт для продакшена

`get_current_manager` (`src/app/web/deps.py`) возвращает Manager с полем
`role` (enum manager/supervisor) — самой ветки по роли там пока нет, гейт
добавляется одной проверкой в прод-версии маршрута: префикс `/admin/...`,
зависимость `manager.role == supervisor`, сессионная кука (та же, что
placement), без DEV_MODE. Для 2FA-пароля — POST-поле, никогда не
логировать. Плюс
rate-limit на `/start` (см. вопрос №1) и аудит-лог «кто подключил какой phone».

## 5. Открытые вопросы

1. **Безопасность /dev/qr в проде.** Сейчас маршрут гасится DEV_MODE — в проде
   404. При выпуске в прод обязательно: supervisor-гейт (см. §4); ограничение
   частоты `ExportLoginTokenRequest` (Telethon может словить FloodWaitError —
   обработать как `error` с ожиданием); CSRF: форма same-origin + кука
   SameSite=Lax (кука уже так ставится) — но для POST-варианта нужен токен.
2. **Блокировка .session при одновременном доступе web+bridge.** В спайке
   не воспроизводится (онбординг нового аккаунта, bridge его не открывает до
   рестарта). Для прод-варианта B вопрос исчезает. Если оставлять A — нужно
   явно запретить QR для аккаунтов со status=active (bridge держит файл).
3. **QR + 2FA-пароль.** Факт №7: `wait()` кидает `SessionPasswordNeededError`,
   затем `sign_in(password=...)`. Значит UI обязан уметь второй шаг «введите
   cloud-пароль», и пароль протекает через web (в варианте B — через БД-команду;
   хранить его нельзя, только транзитом). Решить при дизайне прода.
4. **Параллельные QR-логины.** Dict `account_id → state`: один логин на аккаунт
   (повторный `/start` отменяет предыдущую задачу — есть). Несколько разных
   аккаунтов параллельно — работает (клиенты независимы), но каждый = live
   MTProto-соединение в web + расход лимитов api_id. Для прода — ограничить
   число одновременных логинов (например, 3).
5. **Рестарт web посреди логина.** In-memory state теряется: `/status` вернёт
   404, QR на экране мёртв (токен истечёт сам на сервере). Опасного нет —
   `.session` останется неавторизованным, повторный `/start` начнёт заново.
   Для прода (вариант B) state живёт в БД и переживает рестарт web.
6. **Уникальность phone** (unique-конфликт при перепривязке) — сейчас 409;
   сценарий «перепривязать phone на другого менеджера» не поддержан (вне scope).

## 6. Живой эксперимент — НЕ ПРОВЕДЁН (шаг оператора)

Осталось проверить руками (спайк-код к этому готов):

```bash
DEV_MODE=true .venv/Scripts/python.exe -m app.main web   # локально
# браузер: http://localhost:8000/dev/qr
# 1) заполнить b24_user_id + phone → «Начать (QR)»
# 2) Telegram (телефон) → Настройки → Устройства → Подключить устройство → скан
# 3) дождаться «Готово: аккаунт активен», затем docker compose restart bridge
```

Проверить: (а) QR реально рисуется и сканируется; (б) `.session` появился в
`account_<id>/`; (в) после рестарта bridge аккаунт работает (исходящее
сообщение); (г) поведение при 2FA-пароле (ожидание — `error` с подсказкой).

## 7. Вердикт

**СТРОИТЬ.** Флоу жизнеспособен: Telethon-механика (факты 1-6) полностью
вписывается в request→background-task→poll модель FastAPI; блокеров нет,
единственное реальное осложнение — 2FA-пароль (второй шаг ввода, вопрос №3).

Объём полной фичи (админ-панель): **M** —
вариант B (таблица команд + поллер в bridge + страницы админки за
supervisor-гейтом: список менеджеров, QR-подключение, статус сессий, ввод
2FA-пароля, отвязка аккаунта через `log_out()`). Сама QR-механика — уже
доказана этим спайком (S); рычаг объёма — админ-UI и вариант B.

Оценка усилий по частям: bridge-поллер команд — S; web-админка (список+
QR+2FA+статусы) — M; безопасность (гейт, rate-limit, аудит) — S.

До решения о билде прод-версии live-эксперимент (§6) обязателен — он может
вскрыть сетевые капризы MTProto изнутри docker (IPv6/DC), которые моки не
проверяют.
