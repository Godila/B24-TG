Секция дизайна: Anti-ban и надёжность MTProto

Личный аккаунт через MTProto банится за рассылки. Это главный технический риск.

Лимиты Telegram (по данным Wazzup, проверено эмпирически)
⚠ ЖЁСТКИЙ БАН: создание > 14 новых чатов по номеру за 3 мин
            → блокировка инициации диалогов на НЕДЕЛЮ

✓ БЕЗОПАСНО: отвечать на входящие (без лимита)
✓ БЕЗОПАСНО: писать по @username (нет бана)
✓ БЕЗОПАСНО: < 14 новых чатов / 3 мин с задержками

рекомендация Wazzup: писать по номеру не чаще 1 раза / 3 минуты

Многоуровневая защита (4 слоя)

Слой 1: Throttler (token bucket) — на отправку
            ОТВЕТЫ (входящий→ответ)     ИНИЦИАЦИЯ (новый чат по номеру)
                      │                              │
                      ▼                              ▼
        ┌────────────────────────┐   ┌──────────────────────────────┐
        │ отдельная очередь,     │   │ ЖЁСТКИЙ throttle:            │
        │ высокий приоритет,     │   │ • макс 10 инициаций / 3 мин  │
        │ макс 20 сооб/мин       │   │   (запас от красной линии 14)│
        │ (answers почти не банят)│  │ • мин 5 сек между инициациями│
        └────────────────────────┘   └──────────────────────────────┘
                      │                              │
                      └──────────┬───────────────────┘
                                 ▼
                    ┌─────────────────────────┐
                    │  Глобальный rate limiter │
                    │  (общий потолокTG API)   │
                    └─────────────────────────┘
                                 ▼
                          Telethon send()
Слой 2: Outbox-воркер с retry и backoff
outbox воркер (каждые N сек):
  1. Берёт oldest queued + due (next_attempt_at <= now)
  2. Проверяет throttler → если лимит исчерпан, ждёт
  3. Telethon.send_message()
     ├─ успех → status=sent, обновляем tg_message_id
     └─ ошибка:
        ├─ FloodWait (TG просит подождать X сек) → next_attempt_at += X
        ├─ UserBanned → alert админу, pause очередь инициаций
        └─ сеть/таймаут → экспоненциальный backoff (30с, 2м, 8м, ...)

  max_attempts=5 → после помечаем failed, уведомляем менеджера
Слой 3: Health-чек сессии

Раз в 5 мин проверяем:

  • Telethon client.is_connected()
  • Авторизован ли аккаунт
  • Получили ли FloodWait / AuthKeyError

→ алерт админу если сессия упала

Слой 4: Защита .session файла

.session = ключ к аккаунту:

  • Persistent volume (не терять)
  • Бэкап + шифрование at rest
  • Один процесс = одна сессия
  • Если 2 процесса → TG кикнет одну

Сценарий «аккаунт в бане»

State machine сессии
  ┌──────────┐  входящее   ┌───────────────┐
  │  ACTIVE  │◀────сооб────│ (всегда можем │
  │  (норм)  │             │  принимать)   │
  └────┬─────┘             └───────────────┘
       │ FloodWait / признаки бана
       ▼
  ┌──────────────┐   таймаут прошёл   ┌──────────┐
  │  THROTTLED   │───────────────────▶│  ACTIVE  │
  │ (приёмのみ)  │                    └──────────┘
  └──────┬───────┘
         │持续的FloodWait / SpamBot блок
         ▼
  ┌──────────────┐   алерт админу:      ┌──────────┐
  │   BANNED     │──требуется ручное──▶│  MANUAL  │
  │ (приёмのみ)  │   разблокирование    │          │
  └──────────────┘                      └──────────┘

Важно: даже в бане приём входящих работает — отвечать можно.
Блокируется только ИНИЦИАЦИЯ новых диалогов по номеру.
