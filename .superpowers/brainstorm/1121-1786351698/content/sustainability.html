F sustainability-анализ: где реально узкое место?

Честная оценка нагрузки и единственного слабого места архитектуры.

Где реальная нагрузка vs пропускная способность
УЗКОЕ МЕСТО              ПРОПУСКНАЯ СПОСОБНОСТЬ     РЕАЛЬНАЯ НАГРУЗКА
─────────────────────────────────────────────────────────────────────
FastAPI (HTTP)           ~5 000–25 000 RPS/ядро    < 50 RPS  ✓✓✓ запас x100
Postgres                 тысячи TX/сек              десятки/сек ✓✓✓
Redis                    ~100k ops/сек              десятки/сек ✓✓✓
Telethon (MTProto)       1 аккаунт = ~30 сооб/сек   depends     ✓
  └─ это и есть реальный потолок системы

Единственное спорное решение: всё в одном процессе

Telethon + FastAPI + outbox-воркер в одном контейнере/процессе. Работает, но...
Сравните два варианта:

Как сейчас: 1 процесс (co-located)
┌─────────────────────────────────┐
│  app (один asyncio event loop)   │
│                                  │
│  ┌─────────┐  ┌──────────────┐   │
│  │ FastAPI │  │   Telethon   │   │
│  │  HTTP   │  │  MTProto sess│   │
│  └─────────┘  └──────────────┘   │
│  ┌────────────────────────────┐  │
│  │  outbox воркер (throttle)  │  │
│  └────────────────────────────┘  │
│                                  │
│  общий event loop                │
└──────────────────────────────────┘

+ проще деплой (1 контейнер)
+ проще отладка
− блокировка event loop = падает всё
− краш Telethon = краш API
− рост памяти в одном процессе
Рекомендация: 2 процесса (isolated)
┌────────────────────┐  ┌────────────────────┐
│  web (FastAPI)     │  │  bridge (Telethon) │
│  • HTTP + placement│  │  • MTProto сессия  │
│  • REST API        │  │  • outbox воркер   │
│  • Web UI          │  │  • throttle        │
└─────────┬──────────┘  └─────────┬──────────┘
          │                       │
          └───────────┬───────────┘
                      ▼
            ┌──────────────────┐
            │  Postgres + Redis│
            │  (общее хранилище)│
            └──────────────────┘

+ изоляция сбоев (краш TG ≠ крах UI)
+ независимый рестарт моста
+ можно масштабировать web отдельно
− 2 контейнера вместо 1
  (всё ещё один docker-compose)

Вердикт: FastAPI нагрузку 100% вывезет — это не вопрос, запас огромный. Реальная уязвимость — co-location Telethon с API в одном процессе. Рекомендую разделить на web + bridge (2 контейнера, общий compose) — это даёт изоляцию сбоев почти бесплатно.
