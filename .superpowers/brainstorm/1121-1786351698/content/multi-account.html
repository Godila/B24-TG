🚨 Критическое уточнение: мультиаккаунтность

У каждого менеджера свой TG-аккаунт → система принципиально другая. Это меняет почти всё.

Как я проектировал vs как реально
❌ КАК Я ДУМАЛ (один общий аккаунт):
                   ┌─────────────────┐
   все клиенты ───▶│  1 аккаунт TG   │──▶ маршрутизация/dialog_assigned
                   │  (компании)     │    распределение по менеджерам
                   └─────────────────┘

✅ КАК РЕАЛЬНО (мультиаккаунт):
   клиенты мен.1 ──▶┌─────────────┐
                    │ TG акк #1   │──▶ менеджер Иван (userId=1)
   клиенты мен.2 ──▶│ (его симка) │    b24_user_id=15
                    └─────────────┘
   клиенты мен.3 ──▶┌─────────────┐
                    │ TG акк #2   │──▶ менеджер Петр (userId=2)
                    │ (его симка) │    b24_user_id=23
                    └─────────────┘
                    ┌─────────────┐
                    │ TG акк #3   │──▶ менеджер Анна (userId=3)
                    │ (ее симка)  │    b24_user_id=42
                    └─────────────┘

   Wazzup передаёт userId → битрикс мэтчит с ответственным
   Клиент пишет на акк Ивана → сделка Ивана → карточка по номеру

Что меняется в архитектуре

Раньше: 1 сессия
bridge:
  1 × Telethon client
  1 × .session файл
  1 × throttle queue

просто, но не повторяет Wazzup
Теперь: пул сессий
bridge:
  N × Telethon clients (по менеджеру)
  N × .session файлов
  N × независимых throttle

сложнее, но точно как Wazzup

Ключевые изменения в модели

Новая таблица tg_accounts (привязка аккаунт ↔ менеджер)
tg_accounts                          managers
┌───────────────────────────┐         ┌─────────────────────────┐
│ id           int PK      │         │ id          int PK       │
│ phone         text  UQ     │◀────────│ tg_account_id int FK  │
│ session_path  text         │   1:1   │ b24_user_id   int UQ◀── матчинг
│ status  enum(active,       │         │ name         text        │
│         banned,offline)    │         │ role  enum(manager,..)   │
│ api_id/api_hash (если на   │         └─────────────────────────┘
│   аккаунт)                 │
│ manager_id    int FK 1:1 ◀──────┘  каждый аккаунт = один менеджер
│ last_floodwait_at timestamp│
└───────────────────────────┘

Важное упрощение: 1 менеджер = 1 TG-аккаунт = 1 b24_user_id.
Это жёсткая привязка — не нужно маршрутизировать диалоги.

Как работает матчинг (как у Wazzup)

Поток: клиент пишет → попадает в правильную карточку
1. Клиент (номер +7999...) пишет в TG
2. Сообщение приходит на аккаунт менеджера Ивана (tg_account #1)
3. СРАЗУ знаем ответственного → manager_id=1 → b24_user_id=15
4. По номеру клиента ищем в Bitrix24:
      crm.duplicate.findbyComm (PHONE, "+7999...")
      ├─ найден Контакт → привязываем к существующей Сделке Ивана
      └─ не найден → crm.item.add (Контакт + Сделка, assigned_by_id=15)
5. Пишем в timeline сделки: crm.timeline.comment.add
6. Уведомление Ивану (через im.message.add)

userId Wazzup ≈ manager_id у нас — это и есть "ключ маршрутизации"
который Wazzup передаёт в Bitrix24. У нас это implicit (из аккаунта).
⚠ Что нужно уточнить у заказчика/менеджера:
  1. Сколько примерно менеджеров? (5? 50? 500?) — это определяет архитектуру пула сессий
  2. Менеджер уволился — что происходит с его аккаунтом/диалогами?
  3. Клиент написал менеджеру Петру, а ответственный в CRM — Иван. Что должно случиться?
