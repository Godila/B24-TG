# ЧатМост

**Мост между мессенджерами и Bitrix24** — self-hosted замена сервисов вида Wazzup. Личные аккаунты Telegram и MAX подключаются к облачной CRM: менеджеры ведут переписку с клиентами прямо из Битрикс24, не покидая карточку, а автоматизация — бизнес-процессы и роботы — пишет клиентам теми же аккаунтами.

Вся история переписки — в собственной PostgreSQL (чего не делает SaaS-аналог), мультиаккаунтность (у каждого менеджера своя сессия в каждом канале), защита от бана, отчёт о доставке и прочтении, вложения в обе стороны.

## Возможности

- 💬 **«Чаты» — общий мессенджер** — пункт левого меню Битрикс24: все диалоги менеджера в одном окне. Неотвеченные сверху с возрастом ожидания, счётчик в заголовке вкладки, звук на новый входящий, read-квитанции (⏳ → ✓ → ✓✓).
- 📩 **Виджет в карточках CRM** — вкладка чата через Placement (iFrame) в карточке сделки и лида: история и ответы не выходя из CRM.
- 👥 **Личные аккаунты, не боты** — Telegram (MTProto/Telethon, можно писать первым) и MAX (эмуляция web-клиента, WebSocket). Один менеджер = свой аккаунт в каждом канале; подключение по QR прямо из панели или по share-ссылке.
- 🔁 **Двусторонняя синхронизация с CRM** — входящее → матчинг по номеру → карточка клиента (режим из панели: Контакт+Сделка или только Лид) → канал в поле «Источник» (справочник с маппингом) → комментарий в timeline → уведомление менеджеру. Сконвертированный лид сам перепривязывает диалог к сделке.
- 🤖 **Активити бизнес-процессов** — шаг «ЧатМост: отправить сообщение» в конструкторах БП и роботах на сделках/лидах/контактах: рассылки и автоответы с переменными документа; файл — `[https-ссылка]` в квадратных скобках (скачается и уйдёт вложением). Сообщение уходит в последний диалог сущности; нет диалога — шаг честно падает в журнал БП.
- 📎 **Вложения в обе стороны** — фото/видео/файлы/голосовые: общий медиа-том, лимит 25 МБ, MIME-allowlist, авторизованная раздача, файлы попадают и в timeline карточки.
- 🛡️ **Защита от бана (4 слоя)** — раздельные throttle для ответов/инициаций, outbox-очередь с retry+backoff, обработка FloodWait, health-чек сессий с самолечением.
- 🔧 **Панель управления** — в том же пункте меню: менеджеры и роли (supervisor видит все диалоги), подключение каналов по QR, шаблоны ответов, режим CRM (Сделки/Лиды), маппинг источников, режим read-only.
- 💾 **Вся история у вас** — PostgreSQL + дублирование в timeline Битрикс24; автобэкапы (pg_dump + сессии) с ротацией.

## Архитектура

Интерактивная схема с подсветкой потоков (компоненты, входящее/исходящее сообщение, отправка из бизнес-процесса, путь вложений): **[`docs/diagrams.html`](docs/diagrams.html)** — самодостаточный HTML, открывается локально.

Два процесса в одном Docker-образе (разделение для изоляции сбоев), общаются через Postgres:

- **web** (FastAPI) — placement-обработчики (оболочка «Чаты/Панель», виджет карточки), REST API, вебхуки B24 (установка приложения, хендлер активити БП), статика.
- **bridge** — пул сессий мессенджеров: IncomingHandler (дедуп → persist → задача CRM-синка), OutboxWorker (throttle → отправка → ретраи), CrmSyncWorker (карточки, timeline, уведомления), health-чек.

Ключевые потоки:

- **Входящее**: канал → bridge → дедуп → PostgreSQL → crm_sync → матчинг findbyComm → карточка (лид|сделка) → timeline + уведомление → менеджер видит в «Чатах»/виджете.
- **Исходящее**: менеджер → REST → `Message(pending)` + `OutboxItem(queued)` одной транзакцией → воркер (throttle, FloodWait, backoff) → канал → статусы в UI → timeline.
- **Из бизнес-процесса**: шаг БП → POST на хендлер (авторизация по секрет-заголовку или member_id+self-check) → последний диалог сущности из БД → `[ссылка]`-файл с SSRF-фильтром → outbox → канал (fire-and-forget: доставку тянут ретраи).

## Разработка

```bash
git clone https://github.com/Godila/ChatMost.git
cd ChatMost
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -e ".[dev]"

pytest -v          # 582 теста
ruff check src/ tests/
```

Переменные окружения — см. `.env.example`. Локальная разработка работает без реальных мессенджеров (моки httpx) и без B24 (dev-режим с AUTH-JSON).

## Развёртывание

Production-деплой описан в [`docs/DEPLOY.md`](docs/DEPLOY.md). Кратко:

1. Сервер с публичным IP + домен с A-записью.
2. Локальное OAuth-приложение в Bitrix24 (scopes: `crm`, `im`, `placement`, `user`, `bizproc`).
3. `git clone` на сервер, сгенерировать `.env` (`scripts/gen_prod_env.py`).
4. `docker compose up -d --build` + `alembic upgrade head`.
5. Let's Encrypt TLS + `placement.bind` (`scripts/bind_chats_placement.py`) + регистрация активити БП (`scripts/register_bizproc.py`).
6. Подключить аккаунты менеджеров — QR-онбординг или share-ссылка из вкладки «Панель».

⚠️ После каждого деплоя `docker compose restart nginx` — иначе держит старый IP пересозданного web-контейнера (502).

## Безопасность

- **Auth**: placement-вызов B24 → проверка AUTH_ID через `user.current` (с TTL-кэшем токена) → HMAC-подписанная сессионная кука (httponly, SameSite=none для iframe). Деактивированный менеджер отрезается на каждом API-запросе.
- **Вебхуки B24** (установка, активити БП): секрет-заголовок ИЛИ сверка member_id с порталом из БД + self-check токена `user.current`; fail-closed парсинг чужих payload с редакцией токенов в логах.
- **Активити БП**: SSRF-фильтр `[ссылок]` (https-only, публичные адреса), MIME-allowlist, лимит размера; дедуп повторных вызовов по event_token.
- **Права**: менеджер видит только свои диалоги; supervisor — все, но пишет только в свои. Чужие диалоги — 404 без раскрытия существования.
- **CSRF**: сверка Origin на всех мутирующих запросах (кука SameSite=none летит и кросс-сайтовым POST).
- **Публичные порты**: только nginx (80/443). Postgres — внутри docker-сети.
- **Секреты**: генерируются на сервере, живут в `.env` (chmod 600, в `.gitignore`). 2FA-пароли каналов — только транзит, не хранятся.
- **Идемпотентность**: дубли (MTProto redelivery, MAX reconnect, ретраи очереди B24) отсеиваются по `(dialog_id, external_message_id)` / event_token.
- **Медиа-вложения**: общий docker-том (в БД только метаданные), раздача через авторизованный API, inline — лишь безопасные MIME (SVG/HTML исключены), загрузки ≤25 МБ по allowlist.
